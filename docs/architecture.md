# Overstory Architecture: Providers, Hooks, DI Boundaries, and Command Ownership

This document describes the current architecture contracts used by Overstory for:

- Model provider resolution.
- Claude Code hook wiring and guardrails.
- Dependency-injection boundaries.
- Which commands own which abstractions.

It reflects the current code in `src/` and top-level command wiring.

## 1) Provider Contract

Provider and model contracts are defined in `src/types.ts`, validated in `src/config.ts`,
and resolved at runtime in `src/agents/manifest.ts`.

### 1.1 Config types

- `ModelRef`: either alias (`sonnet`, `opus`, `haiku`) or provider-prefixed string (`provider/model`).
- `ProviderConfig`:
  - `type`: `native` or `gateway`
  - `baseUrl?`: required when `type: gateway`
  - `authTokenEnv?`: required when `type: gateway`

### 1.2 Validation rules

`loadConfig()` in `src/config.ts` enforces:

- `providers.<name>.type` is one of `native|gateway`.
- Gateway providers require both `baseUrl` and `authTokenEnv`.
- Any `models.<role>` that uses `provider/...` must reference an existing provider key.
- Aliases must be one of `sonnet|opus|haiku`.

### 1.3 Runtime resolution contract

`resolveModel()` in `src/agents/manifest.ts` applies this order:

1. `config.models[role]`
2. `agent-manifest.json` default model for that role
3. command fallback model

For gateway providers, `resolveProviderEnv()` returns env overrides injected into tmux Claude sessions:

- `ANTHROPIC_BASE_URL`
- `ANTHROPIC_API_KEY` (empty placeholder)
- `ANTHROPIC_DEFAULT_SONNET_MODEL`
- optional `ANTHROPIC_AUTH_TOKEN` (from `authTokenEnv`)

### 1.4 Commands that own provider/model resolution

These commands call `resolveModel()` directly and therefore own runtime model/provider selection:

- `overstory sling` (`src/commands/sling.ts`)
- `overstory coordinator start` (`src/commands/coordinator.ts`)
- `overstory supervisor start` (`src/commands/supervisor.ts`)
- `overstory monitor start` (`src/commands/monitor.ts`)

## 2) Hook Contract

Hook definitions are JSON with this shape (from `src/agents/hooks-deployer.ts`):

- `hooks.<HookName>[]`
  - `matcher: string`
  - `hooks[]`
    - `type: "command"`
    - `command: string`

### 2.1 Hook sources of truth

There are two hook config sources by design:

- Orchestrator-level canonical hooks:
  - Generated by `buildHooksJson()` in `src/commands/init.ts` to `.overstory/hooks.json`
  - Installed into `.claude/settings.local.json` by `overstory hooks install`
- Per-agent session hooks:
  - Base template: `templates/hooks.json.tmpl`
  - Capability/path/danger guards injected by `deployHooks()` in `src/agents/hooks-deployer.ts`
  - Written to `<worktree>/.claude/settings.local.json` (or project root for persistent agents)

### 2.2 Hook lifecycle events currently used

Current hook events in template/init flows:

- `SessionStart` -> `overstory prime --agent <name>`
- `UserPromptSubmit` -> `overstory mail check --inject --agent <name>`
- `PreToolUse` -> logging + command guards
- `PostToolUse` -> logging + debounced mail check
- `Stop` -> `overstory log session-end ...` + `mulch learn`
- `PreCompact` -> `overstory prime --agent <name> --compact`

### 2.3 Hook payload contract

Hook commands that use `--stdin` consume Claude Code hook JSON payload fields such as:

- `tool_name`
- `tool_input`
- `session_id`
- `transcript_path`

`overstory log` (`src/commands/log.ts`) is the canonical consumer for these payloads.

### 2.4 Guardrail contract

`deployHooks()` composes guard layers in this order:

1. Path boundary guards (`Write`, `Edit`, `NotebookEdit`) using `OVERSTORY_WORKTREE_PATH`
2. Bash danger guard (`git push`, `git reset --hard`, branch naming)
3. Capability guards:
  - Non-implementation roles block write tools and dangerous Bash file mods
  - Builder/merger roles get Bash path-boundary validation for file-modifying commands
  - Native Claude team/task tools (`Task`, `TeamCreate`, etc.) are blocked for all overstory agents

All generated guard commands include the env gate:

- `[ -z "$OVERSTORY_AGENT_NAME" ] && exit 0;`

This prevents hooks from affecting non-overstory Claude sessions at the same project root.

## 3) Dependency Injection Boundaries

Overstory does not use a central DI container. It uses explicit command-level composition and
constructor/factory boundaries.

### 3.1 Stable boundary modules

- Config boundary: `loadConfig()` / `resolveProjectRoot()` (`src/config.ts`)
- Manifest/provider boundary: `createManifestLoader()` / `resolveModel()` (`src/agents/manifest.ts`)
- State stores: `create*Store()` and `openSessionStore()` modules
- Runtime process boundary: `worktree/manager.ts`, `worktree/tmux.ts`
- External service adapters: `beads/client.ts`, `mulch/client.ts`, `mail/client.ts`

### 3.2 Explicit test-time injection points

Current direct injection surfaces include:

- `CoordinatorDeps` in `src/commands/coordinator.ts` (`_tmux`, `_watchdog`, `_monitor`)
- Helper functions with injectable clock/system hooks (for example `calculateStaggerDelay`,
  `isRunningAsRoot`)

Design rule: command files own orchestration; subsystem modules own side effects.

## 4) Command Ownership Matrix

| Abstraction | Command owner(s) | Source modules |
| --- | --- | --- |
| Project bootstrap (`.overstory` scaffold) | `overstory init` | `src/commands/init.ts` |
| Canonical orchestrator hook install/uninstall/status | `overstory hooks` | `src/commands/hooks.ts` |
| Agent hook deployment + guard composition | `sling`, `coordinator start`, `supervisor start`, `monitor start` | `src/agents/hooks-deployer.ts`, `templates/hooks.json.tmpl` |
| Model/provider resolution at spawn | `sling`, `coordinator start`, `supervisor start`, `monitor start` | `src/agents/manifest.ts`, `src/config.ts` |
| Worktree lifecycle | `sling`, `worktree` | `src/worktree/manager.ts` |
| tmux lifecycle + beacons | `sling`, `coordinator`, `supervisor`, `monitor`, `nudge` | `src/worktree/tmux.ts` |
| Session/run registry | `sling`, `coordinator`, `supervisor`, `monitor`, `run`, `status` | `src/sessions/compat.ts`, `src/sessions/store.ts` |
| Hook event ingestion + observability | `log` | `src/commands/log.ts`, `src/events/store.ts`, `src/events/tool-filter.ts` |
| Mail transport + injection | `mail` | `src/commands/mail.ts`, `src/mail/client.ts`, `src/mail/store.ts` |
| Agent/orchestrator context priming | `prime` | `src/commands/prime.ts`, `src/agents/checkpoint.ts` |
| Merge queue + conflict resolution | `merge` | `src/merge/queue.ts`, `src/merge/resolver.ts` |
| Fleet health daemon | `watch`, `monitor`, `coordinator --watchdog` | `src/watchdog/*` |
| Observability queries/views | `dashboard`, `inspect`, `feed`, `trace`, `replay`, `errors`, `logs`, `costs`, `metrics` | `src/events/*`, `src/metrics/*`, `src/sessions/*` |
