# Migration Guide: Providers and Hook Implementations

This guide covers safe migration paths for:

- Integrating or changing model providers.
- Integrating or changing Claude Code hook implementations.

It is aligned to the current Overstory code structure.

## 1) Provider Migration

## 1.1 Config-only provider changes (no code change)

Use this when adding/changing provider entries in `.overstory/config.yaml`.

1. Add or update `providers.<name>`:
   - `type: native` for direct use
   - `type: gateway` with `baseUrl` and `authTokenEnv`
2. Update role model references under `models`:
   - Alias: `sonnet|opus|haiku`
   - Provider-prefixed: `<provider>/<model-id>`
3. Ensure the provider key exists before using provider-prefixed refs.
4. Restart agents that should pick up the new model routing:
   - `overstory sling` (new workers)
   - `overstory coordinator start`
   - `overstory supervisor start`
   - `overstory monitor start`

Why restart: model/provider env is resolved at spawn time by `resolveModel()`.

## 1.2 Code-level provider changes (new behavior)

Use this when changing provider semantics (not just config values).

Update these files together:

1. `src/types.ts`
   - Extend `ProviderConfig`/`ModelRef` contract if required.
2. `src/config.ts`
   - Update defaults/validation rules (`validateConfig`).
3. `src/agents/manifest.ts`
   - Update `resolveProviderEnv()` and/or `resolveModel()`.
4. `docs/architecture.md` and this guide
   - Document new provider type and runtime env contract.

Migration note: command files should not implement provider-specific logic. Keep it in
`src/agents/manifest.ts` so all spawn paths stay consistent.

## 1.3 Provider migration checklist

- [ ] `providers` entries validate successfully.
- [ ] Every provider-prefixed `models.<role>` references a configured provider.
- [ ] Spawned agents receive expected model/env behavior.
- [ ] Architecture and migration docs are updated with the new contract.

## 2) Hook Migration

## 2.1 Choose the correct hook surface

Use orchestrator hook flow when changing project-level opt-in hooks:

- Source: `.overstory/hooks.json` (generated by `overstory init`)
- Installer: `overstory hooks install|uninstall|status`

Use per-agent hook flow when changing runtime guards/logging for spawned agents:

- Base template: `templates/hooks.json.tmpl`
- Guard composer: `src/agents/hooks-deployer.ts` via `deployHooks()`

## 2.2 Orchestrator hook changes

Files to update:

1. `src/commands/init.ts` (`buildHooksJson()`)
2. (if needed) `src/commands/hooks.ts` install/uninstall/status behavior

Rollout:

1. Regenerate canonical source (`.overstory/hooks.json`) via `overstory init` or repo update.
2. Re-install into `.claude/settings.local.json` using:
   - `overstory hooks install --force`

## 2.3 Per-agent hook changes

Files to update:

1. `templates/hooks.json.tmpl` for base command hooks.
2. `src/agents/hooks-deployer.ts` for:
   - Path boundary rules
   - Danger guards
   - Capability-specific guard sets
3. `src/commands/log.ts` and/or `src/commands/mail.ts` when hook command payload/output contracts change.

Rollout behavior:

- New worker sessions pick up changes on next `overstory sling`.
- Persistent agents (coordinator/supervisor/monitor) pick up changes when restarted.

## 2.4 Required invariants when changing hooks

- Keep env gate for overstory-only sessions:
  - `[ -z "$OVERSTORY_AGENT_NAME" ] && exit 0;`
- Preserve worktree boundary enforcement where applicable:
  - `OVERSTORY_WORKTREE_PATH`
- Keep `--stdin` payload compatibility for `overstory log` hook consumers.
- Keep mail injection contract for `overstory mail check --inject`.

## 2.5 Hook migration checklist

- [ ] Correct surface chosen (orchestrator vs per-agent).
- [ ] Hook command payload assumptions documented.
- [ ] Guardrails preserved (env gate, path boundary, dangerous Bash guard).
- [ ] Logging/mail injection behavior remains consistent for active sessions.
- [ ] Architecture docs updated if ownership/contracts changed.

## 3) Combined Provider + Hook Migration (recommended order)

When both systems are changing in the same milestone:

1. Update provider contracts and resolution behavior first.
2. Update hook behavior second (especially if hooks depend on new command flags/payload).
3. Update architecture + migration docs.
4. Roll out by restarting persistent agents and spawning new workers.
